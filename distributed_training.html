1. Why this exists at all

The whole field of distributed training is a response to a very specific problem: modern models don't fit on a single GPU, and even if they did, training would take too long. Two constraints, one solution: use multiple GPUs.

To make this concrete, we'll use a 7-billion-parameter transformer (roughly the size of LLaMA-2-7B or Mistral-7B) as a running example throughout this article. Every technique we cover will be evaluated against the question: does this let us train the 7B?

Before you can appreciate the solutions, you need to feel the problem. So the next section builds up the actual memory cost of training this model on one GPU. When you see that a 7B model needs $\sim$112 GB just for parameters and optimizer state — and an A100 has only 40 or 80 GB — the motivation for everything that follows will click into place.

2. The memory budget of a single GPU

Let's account for everything that has to live in GPU memory during a training step. Assume our 7B model is trained in the standard mixed-precision setup: BF16 forward/backward with an FP32 "master copy" for the optimizer.

Parameters (weights)

7 billion parameters. Two copies:

  • BF16 copy used for the forward and backward passes: $7 \times 10^9 \times 2 \text{ bytes} = 14$ GB.
  • FP32 master copy held by the optimizer to accumulate small updates without losing precision: $7 \times 10^9 \times 4 \text{ bytes} = 28$ GB.

Gradients

One gradient per parameter, held in BF16 during backward. But often accumulated in FP32 to avoid precision loss when summing many small gradients:

  • BF16 gradients: 14 GB (or FP32: 28 GB).

Optimizer state (Adam)

Adam keeps two moments per parameter: the first moment $m$ (running mean of gradients) and the second moment $v$ (running mean of squared gradients). Both are held in FP32 for numerical stability:

  • First moment: $7 \times 10^9 \times 4 = 28$ GB.
  • Second moment: $7 \times 10^9 \times 4 = 28$ GB.

Activations

During the forward pass, every intermediate tensor produced by every layer must be kept in memory so the backward pass can compute gradients. Activation memory is roughly:

$$\text{Activation memory} \approx \text{batch size} \times \text{sequence length} \times \text{hidden dim} \times \text{layers} \times \text{bytes per element}$$

For a 7B model (32 layers, hidden dim 4096) with batch size 8 and sequence length 2048 in BF16, this comes to roughly 40 GB — and it grows linearly with batch size, and often more than linearly if you count attention scores.

An A100 GPU has 40 GB or 80 GB of memory. An H100 has 80 GB. This means: the model does not fit on a single GPU by roughly a factor of two, and that's before we've done anything ambitious with batch size or sequence length.

The number to remember

A rule of thumb for full-precision Adam training: the memory cost is roughly 16 bytes per parameter for parameters + gradients + optimizer state (2 + 2 + 4 + 4 + 4 in the mixed-precision breakdown above), plus activation memory that scales with batch × seq × depth. For a $P$-parameter model, you need $\sim 16P$ bytes just for the training state. A 70B model needs $\sim 1.1$ TB. There is no single GPU on Earth with that much memory. Distributed training isn't optional at scale — it's the only way.

Compute matters too

Even if a model did fit, training would take too long on one GPU. Training a 7B model to convergence on 1-2T tokens takes roughly $10^{22}$ FLOPs. An A100 delivers about 300 TFLOPS in BF16 sustained. That's:

$$\frac{10^{22}}{3 \times 10^{14} \text{ FLOPs/s}} \approx 3.3 \times 10^7 \text{ seconds} \approx 1 \text{ year}$$

Nobody waits a year. Splitting the work across 512 GPUs brings this to under a day — assuming the parallelism is efficient enough to actually deliver that speedup, which is exactly what we're going to learn how to make happen.

3. Communication primitives

Before we can talk about how to split training across GPUs, we need to understand how those GPUs talk to each other. Distributed training is built on a small number of primitive communication operations, and every strategy we'll discuss is a specific choreography of these primitives.

Assume $N$ GPUs, each holding a tensor. The primitives are:

Broadcast

One GPU has a tensor; send an identical copy to all other GPUs. Used for distributing initial model weights to all workers at the start of training.

Reduce

Every GPU has a tensor of the same shape. Combine them (sum, mean, max) and place the result on one designated GPU. The others discard.

All-reduce

The workhorse of data-parallel training. Every GPU has a tensor of the same shape; combine them (usually sum) and give every GPU the result. Equivalent to Reduce followed by Broadcast — but done more efficiently as a single operation.

All-reduce takes tensors from all N ranks and returns the reduced value to all N ranks.

All-gather

Every GPU has a different tensor (a "shard"). Concatenate them all and give every GPU the full concatenated result. Used when we need to reconstruct a full tensor that has been split across GPUs.

Reduce-scatter

Every GPU has a full tensor of the same shape. Reduce them (sum) but give each GPU only one shard of the reduced result. Equivalent to Reduce + Scatter but done in one operation.

A key identity to internalize

All-reduce = Reduce-scatter + All-gather. This decomposition is what makes ZeRO efficient: instead of every worker maintaining a full copy of the gradient after all-reduce (as in data-parallel), workers only maintain their shard (after reduce-scatter), and reconstruct the full tensor only when needed (via all-gather). Same total communication, less memory.

The cost of communication

Two numbers describe an interconnect: bandwidth (bytes per second, dominates for large transfers) and latency (fixed cost per message, dominates for small ones). Rough numbers for reference:

LinkBandwidth (per direction)Latency
NVLink (GPU↔GPU, same node)~300–900 GB/s~1 μs
PCIe Gen4 (CPU↔GPU)~32 GB/s~5 μs
InfiniBand HDR (across nodes)~25 GB/s (200 Gb/s)~1–2 μs
Ethernet 100GbE~12 GB/s~10–50 μs

Two implications: (1) intra-node communication (over NVLink) is roughly $10\times$ faster than inter-node (over InfiniBand), so parallelism strategies that require high-bandwidth communication should be placed within nodes; (2) latency-bound small messages should be avoided in favor of large batched transfers.

Ring all-reduce: why it scales

A naive all-reduce (send everything to one GPU, sum, broadcast back) would send $O(N)$ data through one link, saturating it. Ring all-reduce is the clever alternative that scales linearly with $N$.

Arrange GPUs in a logical ring. Split the tensor into $N$ chunks. In each of $N-1$ steps: each GPU sends one chunk to its neighbor and receives one chunk from its other neighbor, summing incoming into local. After $N-1$ steps, each GPU has one fully-reduced chunk. Then $N-1$ more steps of the same pattern shares those chunks around the ring, so each GPU ends up with the full result.

Total data sent per GPU: $2(N-1)/N$ times the tensor size, which approaches $2 \times$ as $N$ grows. Critically, this is independent of $N$ — the per-GPU communication doesn't grow with cluster size. This is why data-parallel training scales to hundreds of GPUs.

4. Data parallelism — the starting point

The simplest way to use multiple GPUs: replicate the model on each GPU, split the data batch across them, and average the gradients.

Concretely, if you have $N$ GPUs and a global batch of size $B$:

  1. Each GPU holds an identical copy of the model.
  2. Split the batch: GPU $k$ processes examples $(k-1) \cdot B/N$ through $k \cdot B/N$.
  3. Each GPU runs forward + backward on its shard, computing local gradients.
  4. All-reduce the gradients across GPUs (sum, then divide by $N$ for the mean).
  5. Every GPU now has the same averaged gradient; each runs the optimizer step locally.
  6. Since every GPU started with the same parameters, applied the same optimizer step to the same gradient, they end the step with the same parameters.
Data parallel: every GPU holds the full model. Data is split. Gradients are averaged via all-reduce.

What data parallelism buys and doesn't buy

Buys you: throughput. With $N$ GPUs, you process $N$ times more data per step, achieving linear speedup on the training throughput (samples per second). This is exactly what you want when the model fits but you want to finish training faster.

Doesn't buy you: memory. Every GPU still needs to hold the full model, its full gradients, and its full optimizer state. Data parallelism alone cannot train a model that doesn't fit on one GPU. This is the crucial limitation that motivates ZeRO and model parallelism.

5. DDP: how PyTorch actually does data parallel

PyTorch's DistributedDataParallel (DDP) is the standard implementation of data parallelism. Its design has two important tricks worth understanding.

Trick 1: overlap communication with computation

A naive implementation computes the full backward pass, then does one big all-reduce on all gradients, then runs the optimizer. This wastes time because the GPU sits idle during the all-reduce.

DDP is smarter. As soon as a layer's backward pass finishes and its gradients are computed, DDP kicks off an all-reduce on that layer's gradients asynchronously — while the backward pass continues on earlier layers. By the time the backward pass finishes, most all-reduces are already done or nearly done.

Trick 2: gradient bucketing

Doing a separate all-reduce per layer would produce many small messages, each paying the fixed latency cost. DDP groups gradients into "buckets" (typically 25 MB) and all-reduces them together. This trades a tiny amount of overlap for much better bandwidth utilization.

The API in one paragraph

In PyTorch, you initialize a distributed process group (specifying the backend — NCCL for GPUs, Gloo for CPU), wrap your model in DistributedDataParallel, wrap your data sampler in DistributedSampler so each process sees a distinct shard, and launch $N$ processes (one per GPU) with a launcher like torchrun. The framework handles the rest.

The gotcha: batch norm

Regular BatchNorm computes statistics over each GPU's local shard. This makes the effective batch size for normalization purposes $B/N$ instead of $B$, which can hurt training. The fix is SyncBatchNorm, which all-reduces the statistics across GPUs so each layer sees global statistics. Not needed for LayerNorm/RMSNorm (which are per-example anyway), which is another reason those are used in transformers.

6. Gradient accumulation and effective batch size

Suppose your GPU can hold a batch of size 4, but your training recipe calls for batch size 64. Two options:

Option A — data parallelism: use 16 GPUs, each with local batch 4. Global batch = 64. Fast (linear speedup), but expensive (16 GPUs).

Option B — gradient accumulation: use 1 GPU. Do 16 forward+backward passes with local batch 4, but don't call the optimizer yet — just keep accumulating gradients into the same tensors. After 16 micro-batches, average and run the optimizer. Effective batch = 64. Slow (16× as long per step), but only needs 1 GPU.

These aren't mutually exclusive. In practice, if you have $N$ GPUs and want an effective batch size $B$, you might do local batch $b$, accumulate for $A$ steps, giving $B = N \cdot A \cdot b$.

Worked example: hitting a 1M-token batch on 8 GPUs

Say we want an effective batch of 512 sequences × 2048 tokens = 1M tokens per step. On 8 GPUs, per-GPU batch = 64. If each GPU can hold at most batch 4 in memory, we need $64/4 = 16$ accumulation steps. Total forward+backward calls per optimizer step: $8 \times 16 = 128$. Each optimizer step now takes 16× as long as a batch-4 step, but we get the equivalent of a 512-sequence gradient.

Why "effective batch size" matters

Gradient noise scales as $1/\sqrt{B}$: doubling the batch size halves the noise in the gradient estimate. Beyond a "critical batch size" specific to each model, larger batches stop improving convergence per step and start wasting compute. But most modern LLM training runs at effective batch sizes of 1M–4M tokens, which requires both data parallelism and gradient accumulation to reach.

7. ZeRO: sharding the optimizer state, gradients, and parameters

Data parallelism has a memory redundancy: every GPU holds the same optimizer state, the same gradients, the same parameters. On 8 GPUs, we're holding 8 identical copies of everything. That's $7 \times$ wasted memory that could be used for larger models, longer sequences, or bigger batches.

ZeRO ("Zero Redundancy Optimizer," Rajbhandari et al. Microsoft, 2019) is the fix: shard the redundant state across the data-parallel group instead of replicating it. Three stages of increasing aggressiveness:

ZeRO-1: shard the optimizer state

The optimizer state (Adam's $m$ and $v$, FP32 master weights) is the biggest per-parameter cost — 12 bytes per param out of the total 16 bytes per param in mixed precision. In ZeRO-1, only the gradients and BF16 params are replicated on each GPU; the optimizer state is sharded — each GPU holds $1/N$ of it.

How it works:

  1. Forward + backward passes proceed as in DDP (each GPU has full BF16 params).
  2. All-reduce gradients (as in DDP).
  3. Optimizer step: each GPU applies the Adam update only to its shard of the parameters, using its shard of the optimizer state. This produces updated FP32 params for just $1/N$ of the model.
  4. All-gather the updated BF16 params across GPUs so everyone has the full updated model for the next forward pass.

Memory saving: the 8 bytes/param of Adam state ($m$ + $v$) becomes $8/N$ bytes/param. Plus the 4 bytes/param of FP32 master weights becomes $4/N$. Total saving: 12 bytes/param → $12/N$ bytes/param. For $N=8$, that's a $\sim 4\times$ reduction in per-GPU memory for the training state.

ZeRO-2: shard gradients too

In ZeRO-2, gradients are also sharded. Each GPU holds only its shard of the gradients. Communication uses reduce-scatter instead of all-reduce — each GPU ends up with the reduced sum for its shard only, not the full reduced gradient.

Memory saving: on top of ZeRO-1, the 4 bytes/param of gradients (in BF16, or 2 if you're not accumulating in FP32) becomes $4/N$. Total training state: $12/N + 4/N + 2 = (16/N + 2)$ bytes per param, approaching $2$ bytes/param at large $N$.

Communication cost: same as DDP (all-reduce = reduce-scatter + all-gather). We're not adding communication; we're just structuring what we already do differently to save memory.

ZeRO-3: shard parameters too

The final step: shard the parameters themselves. Each GPU holds only $1/N$ of the model's weights at any given time. This requires reconstructing weights on demand during forward and backward passes.

How it works:

  1. Before layer $l$'s forward pass, all-gather the parameters of layer $l$ across GPUs so every GPU has the full weights for that layer.
  2. Run the forward pass for layer $l$.
  3. Immediately discard the gathered parameters (they're only kept as a shard on the owning GPU).
  4. Repeat for the next layer.
  5. During backward, do the same all-gather pattern in reverse.
  6. Gradients are computed and reduce-scattered so each GPU has only its shard.
  7. Optimizer step updates the shard held on that GPU; no all-gather needed since we'll re-gather when we need weights again.

Memory saving: everything is sharded. Per-GPU memory for the training state is $16/N$ bytes/param, plus activations. For $N=64$, this is $0.25$ bytes/param — a 64× reduction from the single-GPU case.

Communication cost: significantly higher than ZeRO-1/2. Each forward pass requires an all-gather per layer; each backward pass does the same. Total communication is roughly $1.5\times$ that of DDP.

8. FSDP — PyTorch's implementation of ZeRO-3

FSDP (Fully Sharded Data Parallel) is PyTorch's native ZeRO-3 implementation. It became the standard in 2022–2023, replacing the older approach of using DeepSpeed's ZeRO plugin.

How FSDP wraps a model

You wrap the model (or specific submodules) with FSDP(model). FSDP breaks the model into "units" (typically transformer blocks) and shards each unit's parameters across the FSDP process group. Under the hood, this creates a set of FlatParameter shards — one per GPU — that FSDP manages.

The forward/backward dance

For each FSDP-wrapped unit:

  1. All-gather the unit's sharded parameters just before its forward pass, reconstructing the full weight tensors.
  2. Run forward, saving activations.
  3. Immediately shard/discard the full parameters (keeping only the local shard).
  4. Repeat for the next unit.

Backward mirrors this: all-gather the unit's params, compute gradients, discard the params, reduce-scatter the gradients so each GPU has only its shard. Then optimizer step operates on shards only.

Prefetch and overlap

To hide the communication cost, FSDP prefetches: while unit $l$ is doing its forward pass, all-gather for unit $l+1$ is already in flight. Well-configured FSDP can keep GPUs busy $\sim 90\%$ of the time despite the extra communication.

The mixed_precision policy

FSDP has an explicit MixedPrecision configuration where you specify: parameter dtype (usually BF16), reduce dtype (dtype for gradients during reduce-scatter, usually BF16 or FP32), buffer dtype. This is a very intentional API — mixed precision + FSDP has many failure modes and being explicit about dtypes prevents them.

When FSDP is not enough

FSDP shards along the data-parallel dimension. If you have 64 GPUs and use FSDP over all of them, you shard 64-ways. But if a single unit's parameters can't fit on one GPU even before sharding (because forward activations of that layer are huge), FSDP alone doesn't help — you need model parallelism, which we get to next.

9. Tensor parallelism — when one layer doesn't fit

Tensor parallelism (TP) splits individual layers across GPUs. Instead of every GPU holding a slice of the whole model in sequence (as in ZeRO-3), each GPU holds a slice of every layer.

The canonical implementation is Megatron-LM (NVIDIA). Its key insight: matrix multiplications can be split along either the input dimension or the output dimension, and if you alternate which one, you can arrange for the communication overhead to be minimal.

Splitting a linear layer: two ways

Consider $Y = XA$ where $X \in \mathbb{R}^{B \times d_{\text{in}}}$ and $A \in \mathbb{R}^{d_{\text{in}} \times d_{\text{out}}}$.

Column parallel: split $A$ along its columns: $A = [A_1 | A_2]$. Each GPU computes $Y_k = X A_k$ (each GPU has the full input $X$ but only a slice of the output). No communication for the forward — but the outputs on different GPUs are shards, so downstream layers need to know.

Row parallel: split $A$ along its rows: $A = [A_1; A_2]$ (stacked). Now $X$ also has to be split accordingly: $X = [X_1 | X_2]$. Each GPU computes $Y_k = X_k A_k$, and the final $Y = Y_1 + Y_2$ requires an all-reduce across GPUs to sum the partial results.

Megatron's pattern for the FFN

A transformer FFN is $Y = \text{GeLU}(X A) B$, where $A: d \to 4d$ and $B: 4d \to d$. Megatron splits $A$ column-parallel and $B$ row-parallel:

  1. $Y_1 = \text{GeLU}(X A_1)$, $Y_2 = \text{GeLU}(X A_2)$ — column split, no communication yet.
  2. $Z_1 = Y_1 B_1$, $Z_2 = Y_2 B_2$ — row split.
  3. All-reduce $Z = Z_1 + Z_2$ — one all-reduce per FFN, at the end.

Why this alternation? Because you can pass column-split outputs directly into row-split inputs without any intermediate all-gather. If instead you used column-parallel followed by column-parallel, you'd need to all-gather in between. Alternating minimizes communication to one all-reduce per pair of layers.

Attention in tensor parallel

Multi-head attention has a natural split: shard heads across GPUs. GPU $k$ gets heads $k \cdot H/N$ through $(k+1) \cdot H/N$. Each GPU computes its heads' attention independently, then the output projection (analogous to $B$) is row-parallel, all-reduced at the end.

The critical constraint

Tensor parallelism requires very fast communication between GPUs because there are two all-reduces per transformer block (one for attention, one for FFN), and they happen inside the forward and backward passes rather than being amortized. In practice, TP is only viable within a single node (over NVLink). Attempting TP across nodes over InfiniBand kills performance.

This means: TP dimension is bounded by the number of GPUs in a single node, typically 4 or 8 on modern systems. You can't shard a layer across 512 GPUs with TP; you'll shard within a node (say 8-way TP) and use other strategies across nodes.

10. Pipeline parallelism — splitting the layer stack

Pipeline parallelism (PP) splits the model along its depth. If your model has 96 layers and you have 8 GPUs, each GPU holds 12 consecutive layers.

A forward pass goes GPU 0 → GPU 1 → ... → GPU 7. Each GPU processes its layers and sends the activations to the next. Backward pass runs in reverse.

Pipeline parallel splits the layer stack. Activations flow forward; gradients flow backward.

The bubble problem

The naive version has a serious efficiency problem. At any given moment, only one GPU is doing useful work: the others are either waiting for input from the previous stage or waiting for their turn. If you plot GPU utilization over time, most of it is empty — the "pipeline bubble."

For a pipeline of $P$ stages processing one batch, the utilization is at best $1/P$. On 8 GPUs you'd be running at 12.5% efficiency, which is unacceptable.

Micro-batching to fill the pipeline

The GPipe (Google, 2019) fix: split each batch into $M$ micro-batches. Start micro-batch 1 on GPU 0, and as soon as it moves to GPU 1, start micro-batch 2 on GPU 0. Pipeline them.

After a startup "fill" phase, all GPUs are busy simultaneously. After the last micro-batch enters, a "drain" phase where GPUs idle in reverse. Utilization becomes $M / (M + P - 1)$ — approaches 100% as $M$ grows.

The catch: micro-batching requires holding all micro-batches' activations in memory until backward, so memory grows with $M$. And activation memory was already the problem we were trying to solve. This is why pipeline parallelism is usually combined with activation checkpointing (§12).

1F1B and interleaved pipelines

PipeDream and Megatron-LM introduced 1F1B (one-forward-one-backward): after the fill phase, alternate forward and backward passes so that activations can be released as soon as their backward pass runs. This reduces peak memory dramatically at the cost of some scheduling complexity.

Interleaved pipelines divide each stage into multiple chunks and interleave them across GPUs, further reducing the bubble at the cost of more communication. Modern Megatron uses this by default for very large models.

11. 3D parallelism — combining everything

For very large models (100B+ parameters), no single parallelism strategy is enough. The standard solution is 3D parallelism: combine data parallelism, tensor parallelism, and pipeline parallelism in three orthogonal dimensions.

Concretely: given $N$ total GPUs, partition them along a $D \times T \times P$ grid where $D \cdot T \cdot P = N$. GPU $(d, t, p)$ is at position $d$ in the data-parallel dimension, $t$ in tensor-parallel, $p$ in pipeline.

A worked example

Training a 175B model on 1024 GPUs

A common configuration:

  • TP = 8 — shard each layer across 8 GPUs within a single node (over NVLink, high bandwidth).
  • PP = 16 — split the layer stack across 16 stages. Each stage is one 8-GPU group.
  • DP = 8 — replicate the whole $8 \times 16 = 128$-GPU pipeline 8 times for data parallelism.
  • Total: $8 \times 16 \times 8 = 1024$ GPUs.

Communication pattern: TP all-reduces happen inside a node (fast NVLink). PP send/recv is one-hop between stages (fast; small message = activations). DP all-reduce is only for gradients, once per step, and happens across the slowest links.

The key design principle: put the most communication-intensive parallelism dimension inside the fastest link. TP is chattiest, so it goes inside a node. DP is chattiest per-parameter but rarest per-step, so it can use the slower inter-node links.

The typical stack in practice

For LLaMA-scale training (7B-70B), most public runs use FSDP alone or FSDP + minor TP. For truly large models (100B+), 3D parallelism is standard. Frameworks that implement 3D parallelism: NVIDIA's Megatron-LM, Microsoft's DeepSpeed, HuggingFace's Nanotron, PyTorch's DTensor / TorchTitan.

12. Activation checkpointing (gradient checkpointing)

Even with parameter sharding, activation memory during forward pass can dominate. For a batch of 8 sequences of length 2048 on a 32-layer 4096-hidden model in BF16, activations alone are 40+ GB.

Activation checkpointing is a classic space-time tradeoff: don't save all activations during forward. Instead, save only a subset (typically one per transformer block) and recompute the rest during backward when they're needed.

The extreme version: save nothing except the outputs of each transformer block. During backward, for each block, recompute its internal activations by re-running its forward pass. The block-boundary activations are cheap to store; the internal activations (attention scores, FFN intermediates) are the expensive ones.

Cost: forward compute goes up by roughly $\sim 33\%$ (you're doing forward-then-forward-plus-backward instead of forward-then-backward). Activation memory drops by $\sim 10\times$ or more, depending on model shape.

In practice, activation checkpointing is essentially free at any scale where you'd actually be training large transformers — the extra compute is small compared to what you can now do with the freed memory (bigger batches, longer sequences).

The interaction with pipeline parallelism

Recall that pipeline parallelism increases peak activation memory by a factor of $M$ (number of micro-batches). Activation checkpointing brings this back down, letting you have both high pipeline utilization and reasonable memory. Almost every real 3D-parallel training run uses activation checkpointing for exactly this reason.

13. Mixed precision in a distributed setting

Mixed precision (§14 of the residuals/normalization article for the single-GPU basics) has additional considerations when combined with distributed training.

Which precision do you communicate in?

DDP all-reduces gradients. In BF16 gradients, the communication is 2 bytes per parameter; in FP32, 4 bytes per parameter. BF16 is faster over the wire but can lose precision on very small gradients.

Standard practice: BF16 for the wire, but the reduction (sum) is done in FP32 to preserve accuracy. NCCL supports this via the reduce-scatter's op parameter. Some setups do the reduction in BF16 too — usually fine for large models where individual gradients are typically not near BF16 underflow.

The optimizer step and the master copy

Adam accumulates tiny updates over many steps. If you did this in BF16, you'd lose those updates to precision — a running mean of small numbers falls below BF16's precision. So the FP32 master copy of parameters is critical: the optimizer step is done in FP32, and then the BF16 copy used for forward/backward is refreshed from the FP32 master.

Loss scaling in FSDP

If using FP16 instead of BF16, loss scaling is needed to avoid gradient underflow (see previous blog). FSDP has a ShardedGradScaler that handles this in a distributed setting — the standard GradScaler doesn't work correctly with FSDP because it wouldn't correctly detect overflow across shards.

14. Debugging distributed training

Distributed training fails in creative ways. Here are the failure modes worth knowing about.

NCCL hangs

The most common failure: the training just stops. All processes are waiting on a collective operation that will never complete because one process took a different code path.

Causes: (1) some rank encountered an error and crashed silently — the others are still waiting for it to participate; (2) shape mismatch between ranks — one rank thinks the tensor is $[B, 768]$, another thinks $[B, 1024]$; (3) some rank went into a Python exception handler that skipped a collective; (4) network flakiness dropped a message.

Debugging: set NCCL_DEBUG=INFO to log every collective and identify where the hang started. Set timeouts on collectives so hangs surface as errors rather than infinite waits. Log per-rank progress with rank prefixes so you can compare.

Silent numerical divergence between ranks

Sometimes ranks don't crash but their gradients diverge — different ranks compute slightly different values that should be identical. After enough steps, the model on different ranks disagrees, breaking the assumption of data parallelism.

Causes: (1) non-deterministic ops (dropout with different seeds, floating-point non-associativity in reductions); (2) different data — a bug in DistributedSampler; (3) BatchNorm using local statistics instead of SyncBN.

Debugging: periodically check that model parameters are identical across ranks via a hash or explicit comparison. If they diverge, bisect: was it identical after init? After first step? After first all-reduce?

Uneven work distribution

Different ranks take different amounts of time to process their shard, so the slowest determines each step. If variance is high, you're bottlenecked on the tail rank.

Causes: variable sequence lengths in a batch (some ranks got longer sequences), padding-heavy vs padding-light batches, straggler GPUs (thermal throttling, hardware faults). Fix: bucket sequences by length so ranks get roughly equal work; monitor per-rank step time to identify slow GPUs.

Out-of-memory (OOM) that happens partway through training

The first few steps work; then step 500 OOMs. Usually caused by memory fragmentation or a slowly-growing tensor (a list that's being appended to and not cleared). Sometimes activation memory grows because of a longer sequence in a specific batch.

Debug: log peak memory each step via torch.cuda.max_memory_allocated(). If it grows over time, something is leaking. If it spikes on specific batches, sequence-length variability is the culprit.

15. Picking a parallelism strategy for your model

The decision tree, roughly:

  1. Does the model + optimizer + activations fit on one GPU with reasonable batch size? Use DDP alone. Simplest to reason about, best throughput per GPU.
  2. Model fits with tiny batch, or doesn't fit at all? Use FSDP (ZeRO-3). Shards everything, brings per-GPU memory down to $O(P/N)$ plus activations.
  3. Activations are the bottleneck? Add activation checkpointing. Almost always worth it for models over ~1B params.
  4. Individual layers so big they can't fit even after ZeRO? Add tensor parallelism inside each node (typically 4- or 8-way, over NVLink). Reserve for models where TP is strictly necessary because it complicates the code substantially.
  5. Even with FSDP + TP + checkpointing, per-GPU memory is still too much? Or communication is the bottleneck? Add pipeline parallelism to split the layer stack across nodes. Most complex option; use only when needed.
  6. Ultra-large (100B+): full 3D parallelism (DP × TP × PP), typically DP=data across replicas, TP inside a node, PP across nodes within a replica.

For most practitioners at LinkedIn-scale — fine-tuning 7B-70B models, doing continued pretraining, distilling large teachers into small students — FSDP + activation checkpointing + BF16 is enough. Full 3D parallelism is only for the largest pretraining runs and is best done through mature frameworks (Megatron, DeepSpeed, Nanotron) rather than rolled by hand.

Interview question bank

These probe both mechanics and design intuition. The "when would you use X vs Y" questions are the ones that separate people who've read the papers from people who've actually trained models.

Question 1 · Motivation
Why do we need distributed training? Walk me through the memory math for a 7B model.

Two reasons. First, the model doesn't fit. In mixed-precision Adam training, the training state costs roughly 16 bytes per parameter: 2 for BF16 params, 4 for FP32 master params, 2 for gradients, 4 for the first Adam moment, 4 for the second. Plus activation memory that grows with batch × seq × depth.

For a 7B model: 16 × 7B = 112 GB just for parameters + gradients + optimizer state, plus ~40 GB of activations at batch 8, seq 2048. Total ~150+ GB. An A100 has 40 or 80 GB, an H100 has 80 GB. It simply doesn't fit.

Second, even if it did fit, training would take too long. A 7B model trained on 1-2T tokens is ~$10^{22}$ FLOPs, which is about a year on a single A100. You need to split across hundreds of GPUs to finish in reasonable time.

Question 2 · Primitives
What is all-reduce and how does it relate to reduce-scatter and all-gather?

All-reduce: every rank has a tensor of the same shape; sum them (or take mean/max), and give every rank the result. This is the workhorse of data-parallel training — it averages gradients across GPUs.

All-reduce is algorithmically equivalent to reduce-scatter followed by all-gather. Reduce-scatter reduces across ranks but leaves each rank with only its shard of the result. All-gather takes shards from each rank and gives everyone the full concatenation.

This decomposition matters for ZeRO. In DDP, after all-reduce, every rank has a full copy of the reduced gradient — wasteful if we're going to shard the optimizer state anyway. ZeRO-2 uses reduce-scatter instead: each rank gets only its shard of the reduced gradient. Same total communication, but memory is sharded. This is one of the core insights that makes ZeRO work.

Efficient all-reduce implementations use "ring all-reduce" — arrange GPUs in a ring, each sends/receives one chunk at a time. Per-GPU communication is $\sim 2 \times$ tensor size regardless of $N$, which is why data-parallel scales to hundreds of GPUs.

Question 3 · DDP
Explain how PyTorch's DDP works. What tricks does it use?

DDP replicates the model on each GPU, gives each GPU a different shard of the batch, and averages gradients via all-reduce so every GPU applies the same optimizer step.

Two implementation tricks matter:

(1) Overlap communication with computation. As soon as a layer's backward pass finishes, DDP kicks off an all-reduce on that layer's gradients asynchronously — while backward continues on earlier layers. By the time backward finishes, most communication is already done.

(2) Gradient bucketing. Doing a separate all-reduce per layer would produce many small messages that pay the fixed latency cost. DDP groups gradients into 25 MB buckets and all-reduces them together — trading a small amount of overlap for much better bandwidth utilization.

Gotcha: BatchNorm computes statistics on local batches, which is now $B/N$ instead of $B$ — use SyncBatchNorm to fix. Not needed for LayerNorm/RMSNorm which are per-example.

Question 4 · Memory sharding
Explain ZeRO stages 1, 2, and 3.

ZeRO shards the redundant per-GPU state that data-parallel replicates. Three stages of increasing aggressiveness:

ZeRO-1: shard the optimizer state only (Adam's $m$, $v$, FP32 master weights — 12 of the 16 bytes per param). Each GPU updates only its shard of parameters, then all-gathers to reconstruct the full BF16 model for next step. Communication same as DDP; memory saves 12/N bytes per param.

ZeRO-2: shard gradients too. Communication uses reduce-scatter instead of all-reduce so each GPU only holds its shard of the gradient. Memory: additionally saves ~4 bytes per param.

ZeRO-3: shard parameters as well. Each GPU holds only 1/N of the model weights at rest. Before each layer's forward pass, all-gather the parameters for that layer, run forward, immediately discard. Same for backward. Per-GPU memory drops to $16/N$ bytes per param — 64× less than DDP for $N=64$.

Tradeoff: ZeRO-3 adds an all-gather per layer per forward and per backward — roughly 1.5× the communication of DDP. FSDP prefetches the next layer's all-gather while the current layer is computing, which mostly hides this overhead.

Question 5 · Comparison
What's the difference between FSDP and DDP? When would you choose each?

DDP replicates the full model on every GPU; FSDP shards it. DDP is simpler and slightly faster per step (less communication) but uses much more memory. FSDP is memory-efficient but has ~1.5× the communication and requires more careful setup.

Use DDP when the model + optimizer state + activations comfortably fits on one GPU. This means models up to maybe 1-3B on A100 (80GB) with reasonable batch sizes. Simplest debug, best throughput per GPU.

Use FSDP when the model doesn't fit under DDP. This is essentially everything above 3-7B params in modern training. FSDP is now the default for LLM fine-tuning and pretraining in PyTorch.

A common pattern: FSDP with wrapping at the transformer-block level (each block becomes a shardable unit). This gives good communication-computation overlap because the units are large enough to warrant the all-gather cost.

Question 6 · Model parallelism
Explain tensor parallelism. Why is it restricted to intra-node?

Tensor parallelism splits individual layers across GPUs. For an FFN $Y = \text{GeLU}(XA)B$ where $A$ goes $d \to 4d$ and $B$ goes $4d \to d$, Megatron splits $A$ column-parallel (each GPU holds a column shard, no communication) and $B$ row-parallel (each GPU holds a row shard, requires an all-reduce at the end to sum partial results). This gives one all-reduce per FFN pair. Attention is similar: shard the heads across GPUs, then all-reduce the output projection.

Why intra-node only: there are two all-reduces per transformer block (one for attention, one for FFN), and they happen inside the forward and backward passes — not batched at the end like DDP's gradient all-reduce. This is a lot of communication per step. It only works fast enough over NVLink (~300+ GB/s intra-node) — over InfiniBand (~25 GB/s inter-node), the communication would dominate compute and the training would slow to a crawl.

In practice, TP dimension is bounded by GPUs-per-node, typically 4 or 8. For scale beyond one node, you combine with pipeline or FSDP.

Question 7 · Model parallelism
What is pipeline parallelism? What's the bubble problem?

Pipeline parallelism splits the model along its depth. If you have $P$ stages and a $L$-layer model, each stage holds $L/P$ consecutive layers. Forward pass goes stage 0 → 1 → ... → $P-1$; backward reverses.

The bubble problem: in the naive version, only one stage is active at a time — the others are waiting. Utilization is $1/P$ — 12.5% for 8 stages, unacceptable.

The fix (GPipe): split each batch into $M$ micro-batches. As soon as micro-batch 1 leaves stage 0 for stage 1, start micro-batch 2 on stage 0. Pipeline fills up. Utilization becomes $M / (M + P - 1)$ — approaches 100% for large $M$.

The cost: holding all $M$ micro-batches' activations in memory until backward. Memory grows with $M$. This is why pipeline parallelism is almost always combined with activation checkpointing.

Advanced schedulers: 1F1B (one-forward-one-backward, from PipeDream) alternates forward/backward so activations can be released as soon as their backward runs — dramatically lower peak memory at the cost of scheduling complexity. Modern Megatron uses interleaved pipelines that further reduce bubbles at the cost of more communication.

Question 8 · 3D parallelism
You have 1024 GPUs and want to train a 175B model. Design a parallelism strategy.

Standard 3D partition. With 8 GPUs per node:

TP = 8 (within a node, over NVLink). Shard each transformer block's attention heads and FFN across the 8 GPUs of one node. This handles the "layers too big to fit" problem.

PP = 16 (across nodes). Split the transformer stack into 16 pipeline stages. Each stage is one 8-GPU node. Use 1F1B scheduling and activation checkpointing to keep memory bounded.

DP = 8 (across replicas). Each replica is $8 \times 16 = 128$ GPUs; run 8 replicas in parallel for data parallelism. All-reduce gradients across replicas once per optimizer step.

Total: $8 \times 16 \times 8 = 1024$ GPUs.

Design principle: put the chattiest parallelism dimension inside the fastest link. TP has all-reduces inside every forward/backward — put it inside a node. DP has one all-reduce per step — it can afford the slower inter-node link. PP has small activation transfers between stages — also inter-node is fine.

For serving optimization gain, replicas can use ZeRO within them (FSDP over the 128 GPUs in a replica) instead of pure DP, further reducing per-GPU memory.

Question 9 · Trade-offs
Explain activation checkpointing. Why is it almost always worth it?

Normally, every intermediate activation from the forward pass is saved for backward. For deep models this is huge — often 30-100 GB just for activations.

Activation checkpointing saves only a subset (typically at transformer-block boundaries) and recomputes the rest during backward. When backward reaches a block, it re-runs that block's forward to reconstruct the internal activations, then computes gradients, then discards.

Cost: forward compute goes up by roughly 33% (each block is forward-passed twice — once during real forward, once during recomputation in backward). But activation memory drops by 10× or more.

Why almost always worth it: the freed memory lets you increase batch size or sequence length, which typically improves throughput per training example by more than the 33% you lost. Net result: often the same or better wall-clock training time, with the ability to train models you couldn't otherwise fit.

Combined with pipeline parallelism: activation checkpointing is basically required for PP because the micro-batches multiply activation memory. Without it, PP's memory explosion nullifies its parallelism benefits.

Question 10 · Practical
Your distributed training run is hanging. What do you do?

Standard playbook:

(1) Enable NCCL debug logs: NCCL_DEBUG=INFO. This shows every collective and where it's stuck.

(2) Set collective timeouts. By default, NCCL waits indefinitely. Set a reasonable timeout so hangs surface as errors with stack traces.

(3) Identify which rank stalled first. Prefix every log line with the rank (some launchers do this automatically). Look for a rank that stopped logging while others continued — that's usually the one that hit an error and stopped participating in collectives.

(4) Common causes: silent OOM on one rank (memory pressure differs between ranks due to data), shape mismatch (a bug where ranks compute different tensor shapes and try to all-reduce mismatched tensors), an exception handler that skipped a collective, a network timeout that dropped a message.

(5) If reproducible on smaller scale: try 2 GPUs instead of 1024. Bugs that show up at scale but not at 2 GPUs are usually networking or synchronization issues; bugs that show up at 2 GPUs too are usually shape/logic issues.

Question 11 · Batch size
How does gradient accumulation interact with data parallelism? Explain effective batch size.

Effective batch size = per-GPU batch × number of GPUs × gradient accumulation steps. All three are independent knobs.

Data parallelism scales throughput linearly: 8 GPUs process 8× more data per step. Increases effective batch by a factor of $N$ at the cost of $N$ GPUs.

Gradient accumulation is single-GPU (or per-GPU) time-multiplexing: do $A$ forward+backward passes with per-GPU batch $b$, accumulate gradients, then run one optimizer step. Effective per-GPU batch becomes $A \cdot b$. Costs $A$× more time per step but no additional GPUs.

Combined: effective batch = $N \cdot A \cdot b$. Choose $b$ as large as memory allows, then use $N$ and $A$ to reach your target effective batch.

Why effective batch matters: gradient noise decreases as $1/\sqrt{B}$, so bigger batches give more stable optimization. Modern LLM training uses effective batches of 1M-4M tokens (McCandlish et al. 2018 "Empirical Model of Large-Batch Training" derives the "critical batch size" beyond which further increase doesn't help). Below that threshold, larger batches help; above it, they waste compute.

Question 12 · Design
You're fine-tuning a 13B model on 8 A100-80GB GPUs. Design the training configuration.

Memory math: 13B params × 16 bytes = 208 GB for training state alone. Doesn't fit on 8 × 80 = 640 GB with any reasonable batch size using DDP (which replicates everything, so per-GPU is 208 GB — over the 80 GB limit).

Configuration:

  • FSDP with wrapping at the transformer-block level, sharded across all 8 GPUs. Per-GPU training state: $208 / 8 = 26$ GB.
  • BF16 mixed precision (native on A100), no loss scaling needed.
  • Activation checkpointing on every transformer block. This frees enough activation memory to increase batch size.
  • Per-GPU batch size: start with 2, increase until OOM.
  • Gradient accumulation: whatever's needed to hit the desired effective batch (e.g., 1M tokens = 512 sequences at 2048 tokens; $512 / (8 \times 2) = 32$ accumulation steps).
  • Optimizer: AdamW, LR warmup 200-500 steps, cosine decay.
  • Gradient clipping: norm at 1.0.

This is a standard modern LLM fine-tuning setup. HuggingFace's Accelerate or Trainer with FSDP config, or TorchTitan, will handle most of the plumbing.

Question 13 · Depth
Why is intra-node communication so much faster than inter-node, and how does that shape parallelism design?

Numbers matter here. NVLink (intra-node, GPU-to-GPU on the same box) delivers 300-900 GB/s per direction. InfiniBand HDR (inter-node) delivers ~25 GB/s. That's a 10-30× gap.

The gap exists because NVLink is a direct point-to-point copper interconnect between GPUs on the same PCB backplane, while inter-node communication goes through NICs, PCIe, external cables, and network switches. Each hop adds latency; each intermediate device adds bandwidth ceiling.

Design implication: place the chattiest parallelism dimension inside the fastest link. Tensor parallelism does an all-reduce inside every transformer block during forward and backward — very chatty. Put TP inside a node. Data parallelism does one all-reduce per optimizer step — much less chatty, can afford the slower inter-node link. Pipeline parallelism sends small activation tensors between stages — also fine over slower links.

This is the fundamental reason 3D parallelism grids look the way they do: TP × DP × PP with TP always kept inside a node. If NVLink bandwidth gets radically better (as with H100's NVLink 4 at 900 GB/s and NVSwitch enabling more GPUs per NVLink domain), the TP dimension can grow — but the intra-vs-inter distinction remains fundamental.

Question 14 · LinkedIn-relevant
You're distilling a 70B teacher into a 7B student on 32 A100 GPUs. What's your setup?

Two models, very different sizes, both need to run at inference time (teacher for labels) and one needs to train (student). Standard approach:

Teacher: load in BF16 with FSDP sharding across all 32 GPUs. 70B × 2 bytes = 140 GB / 32 = ~4.4 GB per GPU. Runs in eval mode only — no gradients, no optimizer state. Very memory-cheap because we don't need the FP32 master copy or Adam state.

Student: load in BF16 with FSDP sharding across all 32 GPUs. 7B training state = 16 × 7B = 112 GB / 32 = 3.5 GB per GPU. Fits comfortably alongside the teacher.

Training loop: for each batch, forward through teacher (no grad) → get soft labels, forward through student → get student logits, compute distillation loss (typically KL divergence between softmax outputs at some temperature $T$), backward through student only.

Configuration: activation checkpointing on both models (teacher's activations dominate memory if not checkpointed), BF16 throughout, per-GPU batch as large as memory allows, gradient accumulation for effective batch.

Optimization opportunity: if the teacher labels are stable over training, precompute them once offline in a first pass, then train the student without running the teacher every step. This is the "distillation dataset" pattern used at Pinterest and LinkedIn for very-large-teacher distillation. Halves per-step compute.

Question 15 · Cross-cutting
Compare DeepSpeed's ZeRO and PyTorch's FSDP.

They implement the same algorithmic idea (ZeRO-3 style parameter/gradient/optimizer sharding). Differences are pragmatic:

Origin. ZeRO came first (Microsoft, 2019); DeepSpeed is the framework built around it. FSDP came later (Meta / PyTorch, 2021-22) as a native PyTorch implementation.

Integration. DeepSpeed is a separate library that wraps PyTorch training loops with its own launcher, optimizer wrappers, and config files. FSDP is native PyTorch — torch.distributed.fsdp.FullyShardedDataParallel wrapping a nn.Module, uses standard PyTorch optimizers.

Features. DeepSpeed has additional features FSDP doesn't natively provide: ZeRO-Infinity (offload to CPU/NVMe), pipeline parallelism built-in, more optimizer variants, MoE support. FSDP has cleaner PyTorch integration and less overhead.

Current trends. The PyTorch team is investing heavily in FSDP (FSDP2, TorchTitan) and it's becoming the standard for open-weight LLM training. DeepSpeed remains popular where its extra features are needed — very large MoE, CPU offload for memory-constrained setups. For a typical LinkedIn-scale fine-tuning or distillation job, FSDP is the current default choice.
